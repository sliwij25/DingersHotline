# Site Navigation Reorg — Design Spec

## Goal

Replace the flat 5-button header nav (repeated across all pages) with a grouped
left sidebar, so pages are organized by category (Home Runs / Strikeouts / Hit
Rate) instead of a single row of equal-weight buttons.

## Scope

In scope: sidebar structure, mobile drawer behavior, stub states for two pages
that don't exist yet. Out of scope: building the K Pick of the Day page, out
of scope: building the Strikeouts Hit Rate view (both are stubbed — see
"Stub pages" below). Out of scope: a true landing/home page — deferred until a
3rd+ prop category is added (see "Future rework" note at the end).

## Hierarchy

Exact grouping and ordering, per user approval:

```
Home Runs
    Pick of the Day      → pick-of-the-day.html
    Today's Picks         → index.html
    Leaders                → leaderboard.html
Strikeouts
    Pick of the Day      → (stub — "soon")
    Today's Picks         → strikeouts.html
    Leaders                → k-leaderboard.html
Hit Rate
    Home Runs             → hit-rate.html
    Strikeouts             → (stub — "soon")
```

Within each group, sub-items always stay visible (no click-to-expand/collapse
— this was explicitly ruled out; see "Future rework" below for why).

## Stub pages

Two leaves have no destination page yet:
- **Strikeouts → Pick of the Day**
- **Hit Rate → Strikeouts**

Both render as disabled sidebar rows: dimmed text, no `href` (or `href="#"`
with a no-op), a small "soon" tag next to the label, `aria-disabled="true"`.
Not clickable. No tooltip/alert needed — the visual state communicates it.

## Layout

- **Desktop (>600px):** Fixed-width left sidebar (~200px), full-height,
  dark navy background (`--navy`, matching the current header's pinstripe
  treatment) so it reads as a nav rail, not page content. Page content sits
  to the right in a flex row. The brand/logo moves into the top of the
  sidebar (replacing its current spot in the header-left block); the
  site-date / "Latest Update" line and Telegram CTA stay in a slim top bar
  above the content area, not in the sidebar.
- **Mobile (≤600px):** Sidebar is hidden by default, slides in as an overlay
  drawer. A hamburger icon appears in the top bar to toggle it; tapping
  outside the open drawer (or a close icon) dismisses it. No JS framework —
  a small inline `<script>` toggling a CSS class, consistent with how the
  rest of the site is built (plain generated HTML, no build step).

## Visual style

Reuse the existing palette and fonts (`--navy`, `--red`, `--gold`, Oswald/
Source Serif 4/JetBrains Mono) — no new design language. Group headers
(Home Runs / Strikeouts / Hit Rate) are bold, slightly larger, non-clickable
labels. Sub-items are indented links; the current page's sub-item gets an
active/highlighted background (mirroring the existing `.nav-link active`
treatment used today for self-links).

## Affected files

All 6 pipeline-generated pages share nav markup duplicated per generator
function in `tools/generate_html.py`:
- `generate_picks_html` (index.html)
- `generate_leaderboard_html` (leaderboard.html)
- `generate_strikeout_leaderboard_html` (k-leaderboard.html)
- `generate_hit_rate_html` (hit-rate.html)
- `generate_k_picks_html` (strikeouts.html)

Plus two static, hand-maintained pages not regenerated by the pipeline:
- `docs/pick-of-the-day.html`
- `docs/player-card.html`

Given the nav markup/CSS is currently copy-pasted per generator function
(confirmed during the K Leaders nav-link work), this reorg should extract a
single shared sidebar-rendering helper (e.g. `_render_sidebar(active_leaf)`
in `tools/generate_html.py`) that all 5 generator functions call, rather than
duplicating the new sidebar markup 5 more times. The 2 static pages get the
sidebar hand-edited in, same as before.

## Future rework (explicitly deferred, not part of this project)

The user plans to expand beyond Home Runs/Strikeouts into more MLB prop
categories (pitcher outs, total bases, hits+runs+RBIs, possibly more). This
sidebar is intentionally scoped for exactly 3 groups and does not need
scroll/collapse handling — when a 3rd+ prop category is added, the nav should
be redesigned from scratch (not patched to scroll). The user's own hunch is
that the eventual design will look closer to a top-tabs + sub-tabs pattern
(the "Option B" layout explored during brainstorming) rather than an
always-expanded sidebar. That decision is out of scope here and should be
revisited as its own brainstorm when the time comes. A true home/landing page
is deferred to the same future trigger point.
